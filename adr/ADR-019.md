# ADR-019: Preserve extended-range color and HDR semantics without making HDR output a first-stable blocker

- **Status:** Accepted
- **Date:** 2026-08-14
- **Decision milestone:** ADR-BOOTSTRAP-001
- **Evidence:** PLANS.md Sections 1.3, 3, 4 (ADR-019), 10, 11, and 26; color/HDR specifications in REFERENCES.lock.
- **Supersedes:** None
- **Superseded by:** None

## Context

Closed color-space enums, `[0,1]` clamping, and Boolean HDR capability would lose gamut, transfer, luminance, range, and presentation information before a backend can choose a truthful output mode.

## Decision

Color encoding is structured from model, primaries, white point, transfer, range, and scene/display interpretation. Finite extended-range components survive public values and canonical codecs until explicit conversion, mapping, or quantization. Pixel format, encoding, alpha, luminance metadata, surface capability, and tone-mapping ownership remain orthogonal. Reference blending/composition uses declared linear-light floating-point intermediates.

## Consequences

Every surface returns an effective presentation configuration and fallback reason. First stable requires tagged extended-range round trips, BT.2020/PQ/HLG reference math, Headless capability simulation, and deterministic SDR mapping, but native HDR/EDR remains disabled per backend until its profile passes.

## Evidence

M3/M8 color corpora and platform profiles validate conversion math, non-finite rejection, profile resources, mapping versions, display changes, precision, screenshots/traces, and capability reporting.

## Replacement

None. Adding encodings, profiles, metadata, or native HDR modes must extend this model without redefining core values.
