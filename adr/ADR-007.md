# ADR-007: Keep low-level memory and host-interop types out of public APIs

- **Status:** Accepted
- **Date:** 2026-08-14
- **Decision milestone:** ADR-BOOTSTRAP-001
- **Evidence:** PLANS.md Sections 3.3, 4 (ADR-007), 6, and 26; public API signature gates.
- **Supersedes:** None
- **Superseded by:** None

## Context

Low-level memory, FFM linkage, and target runtime objects encode lifetime and platform assumptions that would make ordinary application APIs unsafe and target-specific.

## Decision

Internal modules may use stable Java 25 `MemorySegment`, `Arena`, and layouts with explicit ownership. Desktop `Linker`, symbol lookup, function descriptors, and raw handles remain inside generated interop or allowlisted `himari-ffi` support. Common public APIs expose only framework-defined values and typed optional interop handles.

## Consequences

Android, Objective-C, JavaScript, DOM, WebGPU, Wasm runtime, RHI, and native address types cannot leak into common contracts. Speculative ART compatibility does not justify removing stable Java 25 memory APIs internally.

## Evidence

API signature scans, ownership tests, scene-codec constraints, and target isolation gates enforce this boundary at their owning milestones.

## Replacement

None. Any explicit interop escape hatch requires a separate ADR and remains outside ordinary APIs.
