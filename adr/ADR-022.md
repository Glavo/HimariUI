# ADR-022: Run UI work on the platform main thread with explicit continuity and scoping rules

- **Status:** Accepted
- **Date:** 2026-08-14
- **Decision milestone:** ADR-BOOTSTRAP-001
- **Evidence:** PLANS.md Sections 4 (ADR-022), 5.3, 22, and 26; M5-M7 modal-loop and multi-window conformance requirements.
- **Supersedes:** None
- **Superseded by:** None

## Context

A separate UI thread can avoid some host modal-loop stalls but increases IME, accessibility, lifecycle, and reentrancy marshaling across platform-required main threads.

## Decision

For first stable, reactive work, structure, layout, input, and semantics run on the platform-required main execution context. Scheduled UI work and layout animation continue inside OS modal loops through timer-driven reentry, while compositor-eligible animation may continue on the render executor. One reactive graph/state-epoch domain belongs to each application; each window has its own frame scheduler; cross-window invalidation uses ordinary scheduling.

## Consequences

No callback traversal mutates another window's trees, render execution runs no application callbacks, and Windows move/resize/menu loops plus macOS live resize must not freeze required UI work. A dedicated UI-thread model is rejected for first stable.

## Evidence

The Headless event loop establishes the target-neutral owner-context contract: cross-thread ingress is queued, callbacks execute serially on the owner, dispatch and manual-time advancement reject reentrancy, popup ownership is explicit, and multi-window transitions commit before callbacks. `UiScheduler` binds one application `StateDomain` to that owner context, while each `WindowId` receives a separate `WindowFrameScheduler` with independent request generations and redraw coalescing. Ordered event routing selects one matching window, state publication does not broadcast redraws, and requests made during a frame produce one window-local follow-up. The deterministic `m1-scheduler` profile verifies two-window isolation, exact coalesced counts, one sampled frame timestamp, failure containment, and borrowed-resource ownership after shutdown. M5-M7 profiles still measure OS-main-thread enforcement, timer continuity, layout animation, rendering, IME/accessibility reentrancy, cross-window scheduling, and shutdown during native modal loops.

## Replacement

Revisit only through a superseding ADR supported by M5-M7 profiling and conformance evidence.
