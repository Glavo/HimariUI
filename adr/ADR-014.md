# ADR-014: Keep host integration asynchronous and target-specific

- **Status:** Accepted
- **Date:** 2026-08-14
- **Decision milestone:** ADR-BOOTSTRAP-001
- **Evidence:** PLANS.md Sections 3.3, 4 (ADR-014), 5, and 26; target isolation gates and host-driven scheduling profiles.
- **Supersedes:** None
- **Superseded by:** None

## Context

Desktop, mobile, browser, Headless, and remote hosts differ in event-loop ownership, capability timing, worker availability, and native boundary technology.

## Decision

Platform-neutral contracts support host-driven event loops, asynchronous capability acquisition, optional workers, and unavailable capabilities. Desktop uses generated FFM, mobile AOT uses generated target launchers and JNI/NDK or Objective-C/C glue, and browser/Wasm uses generated imports plus isolated JavaScript/browser bindings.

## Consequences

No host boundary becomes a generic provider SPI or leaks target runtime objects into common APIs. Correctness must work on a single host execution context without optional workers or blocking message-pump ownership.

## Evidence

M0 desktop spikes and future A0/W0 isolation profiles validate scheduling, packaging, marshalling, and public-signature boundaries separately.

## Replacement

None.
