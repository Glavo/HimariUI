# ADR-014: Keep host integration asynchronous and target-specific

- **Status:** Accepted
- **Date:** 2026-08-14
- **Decision milestone:** ADR-BOOTSTRAP-001
- **Evidence:** PLANS.md Sections 3.3, 4 (ADR-014), 5, and 26; target isolation gates and host-driven scheduling profiles.
- **Supersedes:** None
- **Superseded by:** None

## Context

Desktop, mobile, browser, Headless, and remote hosts differ in event-loop ownership, capability timing, worker availability, and native boundary technology.

## Decision

Platform-neutral contracts support host-driven event loops, asynchronous capability acquisition, optional workers, and unavailable capabilities. Desktop uses generated FFM, mobile AOT uses generated target launchers and JNI/NDK or Objective-C/C glue, and browser/Wasm uses generated imports plus isolated JavaScript/browser bindings.

## Consequences

No host boundary becomes a generic provider SPI or leaks target runtime objects into common APIs. Correctness must work on a single host execution context without optional workers or blocking message-pump ownership.

## Evidence

`himari-platform-api` now defines typed asynchronous backend/session creation, a nonblocking host-driven event-loop contract, asynchronous window operations, immutable target-neutral snapshots, and opaque surface identifiers without a runtime provider registry or target handle. `himari-platform-headless` implements the contract on one owner execution context while accepting cross-thread ingress, and its deterministic tests cover FIFO/deadline ordering, reentrancy rejection, callback-failure isolation, cancellation, and 5,000 randomized scheduling operations. `himari-runtime` now composes that event loop with bounded cross-thread state batches and per-window frame schedulers: it posts work into host dispatch, never owns a blocking pump, contains application callback failures, and remains correct with no worker thread. The `m1-scheduler` profile records executable owner-context, batching, frame-coalescing, routing, and closure evidence. M0 desktop spikes and future A0/W0 isolation profiles continue to validate target-specific scheduling, packaging, marshalling, and public-signature boundaries separately.

## Replacement

None.
