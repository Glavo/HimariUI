# ADR-021: Contain application callback failures at declared error boundaries

- **Status:** Accepted
- **Date:** 2026-08-15
- **Decision milestone:** M1 / RUNTIME-ADR-001 and phase-failure fixtures
- **Evidence:** Injected structure, measure, placement, paint, effect, cleanup, native-entry, staged-work, retry, and cancellation fixtures in all three M1 candidates; ADR-023; and `./gradlew -g .gradle-user-home :spikes:runtime-decision:conformance`.
- **Supersedes:** None
- **Superseded by:** None

## Context

Application callbacks can fail after reading reactive state or staging topology, properties, effects, resources, and cleanup. Unspecified propagation can expose a partial tree, mix epochs, leak ownership, retry indefinitely, terminate an unrelated window, or unwind through native code. Debug-only containment is insufficient because release applications require deterministic lifecycle and presentation behavior too.

## Decision

Every application callback executes within an explicit runtime error-boundary chain. The innermost active boundary owns a failure from structure, measure, placement, paint, effect mount/update, cleanup, event handling, or measure-time materialization. The failed attempt is aborted atomically, all staged owned work is cleaned, and the prior committed tree and presentation targets remain authoritative until a separate recovery commit succeeds.

A boundary may declare framework-safe fallback content. After cleanup, the runtime schedules that fallback as a fresh UI attempt; it is never spliced into the failed draft. If fallback construction fails, the same boundary is not re-entered: the failure escalates once to the next active parent. Nested boundaries therefore contain at the nearest healthy ancestor. If no healthy boundary remains, the runtime keeps the last committed scene for the current frame, marks the affected window runtime failed, stops further application callbacks for that window, and reports the root failure without terminating unrelated windows or the host loop.

A failed boundary remains failed until an explicit reset/retry action or a separately declared recovery policy advances it. The runtime must not retry automatically in the same epoch or frame. A retry creates a new attempt and either commits completely or returns to the same contained state.

Effect or resource cleanup runs child-before-parent and continues after individual cleanup failures. Cleanup failures are aggregated under the original boundary, include stable owner identities, and cannot reactivate or retain logically disposed work. A failed effect mount cleans every staged effect/resource from that attempt before fallback is scheduled.

Every failure emits a stable diagnostic code and structured trace containing the available source location, owner/group/key path, and explicit recovery action. Debug builds may attach stack detail and present a framework-owned diagnostic overlay. Release builds omit sensitive diagnostic detail and show only declared fallback content; if none exists, they retain the last committed scene and disable the failed window runtime as described above. Debug and release behavior cannot differ in atomicity, ownership, cleanup order, boundary selection, or retry state.

All native callback entries catch `Throwable`. No application or framework failure may unwind through an upcall. The entry records the error into the owner-context error queue and applies the same boundary policy there. A VM-fatal condition may bypass application fallback work after containment, but it still cannot unwind into native code and must mark the affected host/runtime failed deterministically.

## Consequences

`STRUCTURE-001`, `MOUNT-001`, `EFFECT-001`, phase callbacks, input delivery, and platform upcalls share one boundary identity and diagnostic vocabulary. Boundary state participates in the UI commit protocol rather than being an exception handler that mutates mounted nodes directly. Error fallback is application-visible topology and must have stable identity, accessibility semantics, and deterministic Headless output.

Application callbacks may throw, but they cannot rely on propagation to the platform loop or on implicit repeated execution. Cleanup implementations must be independently idempotent enough for aggregation and shutdown. The root policy keeps other windows and the event loop alive when the affected runtime can be isolated.

## Evidence

The frozen explicit-boundary fixture injects all seven callback categories and requires an unchanged committed revision until recovery, deterministic fallback, stable codes, quality-four traces, and balanced post-close nodes, owners, effects, edges, retained bytes, staged mutations, and callbacks. The staged-work fixture verifies abort cleanup and explicit retry; the selected grouped candidate additionally passes cooperative-cancellation cleanup. Every candidate passes all 13 fixtures on the JVM and in Native Image with zero disqualifications.

The three prototypes demonstrate the same nearest-declared-boundary outcome through different storage models. The RUNTIME-ADR-001 review fixes the nested rule, fallback escalation, explicit retry gate, cleanup aggregation, root-window isolation, and release-build policy above before production implementation. These clauses are normative conformance requirements for the selected grouped runtime; their production nested-boundary and release-mode fixtures belong to `STRUCTURE-001` rather than remaining open architecture choices.

## Replacement

Replace this ADR only if production evidence requires a different containment unit, root-failure product policy, or asynchronous recovery model. A replacement must preserve atomic commit, complete cleanup, nearest-boundary determinism, native-entry containment, stable diagnostics, bounded retry, multi-window isolation, and equivalent debug/release ownership semantics.
