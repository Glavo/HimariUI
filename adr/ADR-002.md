# ADR-002: Use FFM as the only desktop FFI and generate typed bindings

- **Status:** Accepted
- **Date:** 2026-08-14
- **Decision milestone:** ADR-BOOTSTRAP-001
- **Evidence:** PLANS.md Sections 1.4, 2, 4 (ADR-002), and 26; JEP 454 and Java 25 FFM specifications in REFERENCES.lock.
- **Supersedes:** None
- **Superseded by:** None

## Context

Multiple native backends would duplicate ABI behavior, enlarge the runtime graph, and make JVM and Native Image behavior diverge.

## Decision

Desktop targets use generated, fixed-signature Java FFM bindings and shared allowlisted FFM support. Calls use typed Java methods or `MethodHandle.invokeExact`; there is no FFI provider SPI, runtime backend selection, JNA production path, reflective dispatch, or `Object[]` invocation.

## Consequences

Generated bindings are the sole desktop system-call path on both the JVM and Native Image. Mobile host glue and browser/Wasm imports are separate target and packaging boundaries, not alternative desktop FFI providers.

## Evidence

M0 owns schema generation, downcall/upcall, ABI probe, platform spike, native-load, and Native Image evidence. Until those pass, M0 remains open but the architectural choice is binding.

## Replacement

None. Failure of shim-free FFM on a platform requires a new replacement ADR before that platform proceeds.
