# ADR-002: Use FFM as the only desktop FFI and generate typed bindings

- **Status:** Accepted
- **Date:** 2026-08-14
- **Decision milestone:** ADR-BOOTSTRAP-001
- **Evidence:** PLANS.md Sections 1.4, 2, 4 (ADR-002), and 26; JEP 454 and Java 25 FFM specifications in REFERENCES.lock.
- **Supersedes:** None
- **Superseded by:** None

## Context

Multiple native backends would duplicate ABI behavior, enlarge the runtime graph, and make JVM and Native Image behavior diverge.

## Decision

Desktop targets use generated, fixed-signature Java FFM bindings and shared allowlisted FFM support. Calls use typed Java methods or `MethodHandle.invokeExact`; there is no FFI provider SPI, runtime backend selection, JNA production path, reflective dispatch, or `Object[]` invocation.

## Consequences

Generated bindings are the sole desktop system-call path on both the JVM and Native Image. Mobile host glue and browser/Wasm imports are separate target and packaging boundaries, not alternative desktop FFI providers.

## Evidence

`tools/ffi-schema` implements the first target-resolved canonical ABI model, strict deterministic JSON codecs, semantic validator, fixed-signature Java generator, Native Image metadata generator, and native-probe protocol. It generates exact exported-function and unbound function-pointer downcalls, exception-containing upcalls, typed immediate `errno` or `GetLastError` results, callback-adapter reachability metadata, and exact foreign-stub registrations. `spikes/ffi-ffm` exercises the portable path against the host C runtime without a project-built native shim. `spikes/abi-probe` compiles a non-published C17 executable and compares its deterministic type, aggregate, bitfield, callback, structure-return, and variadic-call measurements with the schema and generated Java layouts. `spikes/win32` uses the same generator for real User32, Kernel32, DisplayConfig, DXGI, and COM-vtable calls; its executable profile verifies window lifecycle, WndProc reentrancy and exception containment, immediate failure capture, native ownership teardown, and a dynamic output/Advanced Color snapshot. `spikes/d3d12` extends that path through real D3D12 and DXGI COM vtables, including the Windows-specific lowering of structure-return methods, and verifies device, queue, flip-model swapchain, barriers, fence synchronization, exact GPU clear readback, debug-queue diagnostics, process budgets, and deterministic COM teardown. `spikes/native-image-ffm` packages those same generated classes and per-schema metadata into a no-fallback GraalVM Native Image executable; the Windows x64 profile passes exact reachability analysis, portable dynamic-upcall/lifetime checks, a real D3D12 window clear and readback, direct system-library load auditing, and Native Image process budgets without an SVM system-call backend. The `m0-ffi-schema`, `m0-ffi-ffm`, `m0-abi-probe`, `m0-win32-window`, `m0-d3d12-surface`, and `m0-native-image-ffm` profiles record their commands and evidence artifacts. M0 still owns the remaining target matrix and platform spikes; until those pass, M0 remains open but the architectural choice is binding.

## Replacement

None. Failure of shim-free FFM on a platform requires a new replacement ADR before that platform proceeds.
